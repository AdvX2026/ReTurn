# apps/ReTurn — Agent Notice

- SwiftUI multiplatform Xcode project (deployment targets iOS 17.0 / macOS 14.0), built with Xcode 26. MVP UI implementation and demo verification prioritize iOS/macOS 26. Prefer native OS-26 SwiftUI behavior over hand-drawn approximations; preserve the older deployment targets with small, localized `#available` branches and standard-system fallbacks unless the user explicitly changes the minimum versions. visionOS removed. macOS App Sandbox is OFF per PRD §6.1 (sandbox without outgoing-network entitlement blocks LAN access to Pi/sampler).
- Use root `./script/build_and_run.sh` as the single macOS kill + clean-build + run entrypoint; `--verify` also confirms the launched `ReTurn` process, and the Codex `Run` action invokes the same script.
- `project.pbxproj` uses synchronized folder groups: any file added under `ReTurn/` / `ReTurnTests/` is picked up automatically — never hand-edit the pbxproj to add files.
- Xcode 26 builds this target as a mergeable library: the ~58 KB `ReTurn` executable is a stub and the real code lives in `ReTurn.app/ReTurn.debug.dylib`. Incremental `xcodebuild build` has silently no-oped over on-disk source changes here and shipped a stale dylib to the simulator — always `xcodebuild clean build` before install-and-verify. `xcodebuild test` runs on a "Clone" device in a separate device set that `xcrun simctl list` cannot see; capture visual evidence via `XCTAttachment` + `xcrun xcresulttool export attachments --path <xcresult> --output-path <dir>` instead of `simctl io screenshot`.

## SwiftUI source layout

- `ReTurn/App` owns only app and platform composition roots. `AppRootView` selects `IOSRootView` or `MacRootView` at compile time: iOS uses the reviewed `HomeTimelineView`, while macOS uses its own pager/calendar/Gantt product layout.
- `ReTurn/Core` owns the shared contract mirror and transport, `ReTurn/DesignSystem` owns cross-feature tokens/components, and `ReTurn/Features` is feature-first with platform folders below a feature where its UI is platform-specific.
- Keep shared state and pure projection logic above platform views when they land. Do not force iOS and macOS layouts into one configurable view, and do not promote a view into `Shared` until it has a second real platform caller.

## iOS/macOS 26 UI policy

- Prefer system components that adopt Liquid Glass automatically. For eligible custom navigation/control surfaces, use native APIs such as `glassEffect`, `GlassEffectContainer`, and glass transitions instead of recreating highlights, refraction, glow, or shadows.
- Keep Liquid Glass in the functional navigation/control layer. Plain `Label`, text, symbols, and content backgrounds do not receive glass directly; they use semantic foreground styles inside the glass-bearing control or surface.
- Use `.interactive()` for genuinely interactive custom glass controls. Choose `regular` by default and reserve `clear` for media-rich backgrounds where its contrast requirements are satisfied.
- Do not layer custom highlight, glow, blur, or shadow artwork on top of native Liquid Glass. Older systems may use a simple standard Material fallback, without attempting to perfectly imitate OS 26.

## Models.swift (shared-contract mirror)

- Mirror basis: latest `origin/main` — includes `CollectionStatus`, `Usage*`, singleton `UserProfile`, and effective profession fields on `StatsTodayResponse`; no `ContinueResponse`/`degraded`. Keep `packages/shared` and this mirror in the same commit (AGENTS.md contract rule).
- Decode/encode ONLY via `ReTurnAPI.makeDecoder()/makeEncoder()` — snake_case conversion lives in the coder strategy; models deliberately have no per-field CodingKeys.
- Enum policy: all mirrored string enums are tolerant (`TolerantEnum`) — unknown raw values decode to a fallback, never throw. `NodeKind` currently mirrors `email`, `vscode_recent`, and `browse_history`; future server values still must not crash older app builds.
- Card `content` is loose JSON in the contract; the mirror decodes it into typed per-`type` structs (shapes taken from what `services/save.ts` / `services/chat.ts` actually write on the mirror basis) with a `.raw` fallback on unknown type or shape drift. If backend tightens/changes card content, update `BriefingCardContent` & co. and `ModelsTests`.
- Weekly cards decode as `WeeklyCardContent` and render in After as a seven-day recap with the opening line, summary, and up to three highlights.
- IDs and timestamps are plain `String` (server stamps `created_at`; parse display dates via `ReTurnAPI.parseDate`). `client_uuid` is the idempotency key — never regenerate on retry.

## APIClient.swift

- Transport only: typed async methods over URLSession for every Pi endpoint (port 8787). No caching, no outbox, no retries — those belong in the stores (PRD §5.2). LLM-backed calls (save/chat/ask/resume/voice/intent) use a 180 s per-request timeout; plain reads use the URLSession default.
- Health upload sends the fixed token as `x-return-token`. Fastify error bodies (`{statusCode, error, message}`) surface as `APIError.http`.
- Networking config lives in `apps/ReTurn/Info.plist` (deliberately OUTSIDE the synchronized `ReTurn/` folder — inside it, the sync group copies it into Copy Bundle Resources and Xcode warns). It merges with `GENERATE_INFOPLIST_FILE=YES` via `INFOPLIST_FILE=Info.plist` and carries `NSAppTransportSecurity.NSAllowsLocalNetworking` (scoped, NOT arbitrary loads) plus iOS `NSLocalNetworkUsageDescription`. Add future plist keys here, not as INFOPLIST_KEY_ build settings for dict-valued keys.


## AppStores / live API

- `AppStores` owns `APIEnvironment` + domain stores (`TimelineStore`, `ChatStore`, `CardsStore`, `StatsStore`, `ProfileStore`, `SaveStore`, `TasksStore`, `NodesStore`, `SearchStore`, `HealthStore`, `UsageStore`). Views take only the stores they use via `@Environment`.
- Every Pi route in `docs/api.md` is reachable from a store method; transport stays in `APIClient`. Optional `API_TOKEN` and `HEALTH_TOKEN` are user-editable (Settings / connection recovery). UI outbox for `POST /api/nodes` is `NodesStore` JSON queue under Application Support.
- Pi `messages` remain durable archive data, but the visible conversation is scoped to one App process lifetime: the first successful `/api/messages` page becomes a hidden baseline, later polling surfaces only messages first observed after that baseline, and repeated Resume results collapse to the latest one. Do not delete server messages to clear the UI; Task records and archived Inputs still reference them.
- Before/Now/After data pages are live (not fixture-only). Fixtures remain for previews and `CardGallery`; iOS Now reads live dimensions/effective profession from `StatsStore` and the greeting name from `ProfileStore`.
- `Info.plist` contains HealthKit usage text, but the Xcode project currently has no HealthKit entitlement/capability. Simulator builds do not prove real-device HealthKit authorization; add and verify the entitlement before relying on uploads in production.

## Main timeline UI

- macOS has its own product layout: `AppRootView` selects the iOS horizontal pager or `MacRootView`. Desktop layout metrics live in `ReTurnDesign.Desktop`; `MacRootView`/`MacBeforeView`/`MacAfterView`/`MacCalendarView`/`MacDayTimelineView` are `#if os(macOS)`.
- `MacRootView` IS the iOS pager structure: horizontal `ScrollView` + `scrollTargetBehavior(.paging)` + `scrollPosition(id:)`, so trackpad two-finger swipes and Magic Mouse swipes turn pages natively (an earlier NavigationSplitView sidebar and a simulated `.move` transition were both rejected — the sidebar turned a time flow into a document switcher, the transition duplicated what the pager gives for free). Keyboard (←/→ step, Escape returns to Now, ⌘1/2/3 jump), floating window-edge arrows and the clickable top label row all drive the same `scrollPosition` binding; arrow/Escape shortcuts are `.disabled` while the composer is focused so text editing keeps its cursor keys.
- The Timeline layer (models, event views, `TimelineDesignTokens`) is shared by both platforms; `BeforeView`/`TimelineView` are used by iOS only, while macOS `MacBeforeView` is its own browser: `MacCalendarView` (month grid, event dots, locale-first weekday order) + `MacDayTimelineView` (one continuous horizontal Gantt across every loaded day with content — not per-day cards; span bars with greedy overlap lanes, sleep lane, input symbol dots, ambient baseline dots, hover `.help` tooltips; fixed compact height from `timelineTrackHeight` / `timelineTrackVisibleLanes`) + a detail list reusing the shared event views. Selecting a track/list item expands `TimelineSampleDetailView` under the row with the full projection `meta` (no second fetch). The track sits in its own horizontal ScrollView and OPENS at `timelineDefaultZoom` (2×) so swiping over it always browses time — free pan across the full range, no day paging. Zoom runs 1…`timelineMaxZoom` (8×) via trackpad pinch or the always-visible −/+ controls; ticks switch 3h → 1h once an hour is `timelineDenseTickHourWidth` wide; midnight ticks carry a date label. At zoom 1 one day fills the viewport and further swipes fall through to page turning; nested same-direction scroll chaining handles the handoff. Track width is explicit (viewport × zoom × dayCount) via `onGeometryChange`, NOT a GeometryReader. Calendar / day-stepper / item selection scroll the track to that day. TimelineDesign colors carry per-OS branches — named system accents resolve through a `AccentColor` typealias, grouped-background/fill colors have explicit macOS mappings.
- Timeline projection is thickened on the server (`packages/server` `buildTimeline`): app/agent spans keep presence bars; all sampler point kinds (`ACTIVE_FEED_KINDS` + browse_history / tab_sample / git_commit / reminder / vscode_recent / email / todo_check) emit feed segments with rich labels and full `source_meta` (+ title/content) in `meta`. Agent labels are `provider · project`. Client `TimelineDisplayItem` keeps that meta and derives subtitle/detail fields while retaining the reviewed iOS major/point/span defaults; `MacDayTimelineView` separately maps agent sessions to bars and browse/tab/git/vscode samples to ambient track salience.
- The current Main timeline/composer design is iOS-only. macOS uses a different product layout; keep iOS-specific layout and interaction changes behind `#if os(iOS)` unless a separate macOS design is explicitly provided.
- `HomeTimelineView` is a horizontal Before / Now / After pager, defaulting to Now. The top navigation and the swipe position share one `TimelinePage` selection.
- iOS Now is the reviewed Canvas mascot hero only. `NowActionBar`, `NowConversationView`, `SaveTodayButton`, `SaveResultLine`, and the inline connection status are macOS-only UI; do not gate the iOS hero on `ChatStore.entries` or compose those desktop controls back into it. The shared Store/API wiring remains available to the iOS composer.
- `ComposerBar` lives in its own file and is shared by both roots. It sends text/voice/image/file inputs through `ChatStore`, and queues offline text nodes through `NodesStore` without changing their `client_uuid` on retry.
- That navigation is three plain labels, deliberately **not** a segmented `Picker` — the filled capsule was the only opaque surface on the screen and outweighed the flat mascot and translucent composer around it. Each label lays out at its `.semibold` width with the live text overlaid, so selection weight changes cannot shift the row.
- The row dims to `navigationDimmedOpacity` when idle rather than hiding, so the current page stays readable, the row keeps hinting other pages exist, and the labels stay tappable (opacity does not affect hit testing). On iOS, a full-width adaptive system-background gradient sits above timeline content and below the labels; it resolves white in Light Mode and black in Dark Mode, then fades toward the bottom. Keep this backdrop outside the label dimming modifier so it remains at full strength while chrome is visible; macOS does not receive this Before-specific visual. `TimelinePageNavigation` keys its `.task(id: Activity(...))` on the page, combined pager/Before scroll activity, and chrome visibility: a non-idle phase holds full strength without counting down, and the countdown starts on the restart that follows scrolling going idle. Do not key it on `selectedPage` alone — `scrollPosition` updates when the settle animation *begins*, which is both too late to feel responsive to the drag and too early to measure "settled". `onScrollPhaseChange` is iOS 18 / macOS 15, so it sits behind availability branches; older systems degrade to waking on the page change. Also note `try? await Task.sleep` swallows cancellation — the `guard !Task.isCancelled` after it is required, or superseded timers dim right after their replacement restored full strength.
- The initial Now visual follows Figma file `ilZuF3hqB1HH7f1usiMmPM`, node `7:1182`. Shared HIG colors, spacing, semantic typography, and adaptive layout rules live in `DesignTokens.swift`; do not scatter replacement literals through views.
- The iOS Before page loads the trailing seven days through `TimelineStore`, preserves the reviewed timeline presentation, and opens historical briefing cards from the store. `TimelinePreviewData` is preview-only.
- The iOS After page keeps the reviewed Suggestions / Ideas grouping while projecting live `CardsStore` records. Todo rows support done, Apple Reminders acceptance, dismiss, and per-row errors; macOS renders the same typed cards in an adaptive grid. `AfterPreviewData` is preview-only.
- Timeline chrome uses the available container width with compact-screen insets and readable iPad caps. On iOS, the bottom chrome keeps both controls mounted: Now reveals the composer, while Before and After reveal the Settings-style search field. This preserves both drafts across page changes. The composer expands with a spring animation while focused and grows vertically from one to five text lines before scrolling internally; preserve this responsive behavior instead of restoring device-specific widths or a single-line field.
- On iOS/macOS 26, the composer surface uses the native interactive `glassEffect`; do not add manual highlight, glow, or shadow overlays on top. Older systems retain the standard Material fallback.
- `Kongkong.imageset` is the exact vector exported by Figma (`preserves-vector-representation`). Cards and macOS keep this static `MascotImage`; the iOS Now page is the only sanctioned Canvas redraw. Both variants keep their width sourced from the scroll viewport, never from a container size that the keyboard or composer animation can change.
- `HomeTimelineView` / `NowPage` / `ComposerBar` are deliberately separate files and views, and the screen uses **no `GeometryReader`**. `ComposerBar` owns the draft text so typing cannot invalidate the pager; adaptive widths are `.frame(maxWidth:)` + `.padding(.horizontal:)` and page frames are `.containerRelativeFrame`. Reintroducing a `GeometryReader` around the pager re-couples the composer's spring animation to a full pager relayout on every frame.
- The composer's attachment `Menu` is a single control inside the glass content layer; `.buttonStyle(.plain)` suppresses the bordered pressed state the system otherwise draws around the glyph. Its touch target reaches the 44pt minimum via `padding(hitPadding)` → `contentShape(.rect)` → `padding(-hitPadding)`; never clip it to the glyph bounds (`clipShape`/`contentShape` around a `.title2` symbol yields a ~20pt target, and `clipShape` clips hit testing too).
- Opening the attachment menu merges the composer's `glassEffect` surface into the menu, so the input field is not visible while the menu is open. **This is accepted behavior, not a bug — do not "fix" it.** It is iOS 26's Liquid Glass presentation language (the menu grows out of its source surface), and the user chose to keep it rather than fight it.
- Should that decision ever be revisited, these are already ruled out: `.buttonStyle(.plain)` (removes the pressed box, not the merge); a UIKit `UIButton` + palette `UIMenu` via `UIViewRepresentable` (tried and reverted in e2022be — UIKit presentation merges too); a transparent second `Menu` layered outside the glass (avoids the merge, but the two-layer structure was rejected as inelegant). Untried: `GlassEffectContainer` + `glassEffectUnion` to give the plus its own morph identity, or a self-drawn panel — which is how ChatGPT's iOS app does it (its attachment sheet is not a system menu: circular icon backings, leading icons and ~40pt corners are all outside what `UIMenu` renders).
- The iOS composer needs its own `contentShape` + tap-to-focus: the `TextField` only covers one text line, so the surface's vertical padding is otherwise dead and taps there do not raise the keyboard.

## Now mascot

- iOS Now uses `MascotView`, a native Canvas renderer with profession accessories and stat-driven intake/focus/output/continuity/energy effects. `MascotProfession` remains renderer presentation state; `NowPage` maps the shared profile `Profession` into it at the view boundary.
- All renderer constants use the original 175×150 core coordinate space. The Canvas applies one padded stage transform for orbiting effects; do not introduce a second coordinate system or `GeometryReader`.
- The Canvas `TimelineView` runs only while Now is selected, the scene is active, and Reduce Motion is off; live stats do not change that lifecycle gate.
- The mascot is a native `Button`. Reduce Motion pauses continuous animation and replaces the 26pt hop with opacity feedback; leaving Now or backgrounding the app pauses Canvas refresh. Keep static `MascotImage` in cards and macOS.
- The right arm mirrors the left arm's rectangle, pivot, and base angle; do not restore the asymmetric raised-arm coordinates from the original Figma pose.
- Idle wave / cheer / twirl emotes run only while continuous motion is allowed. Their scheduler is a `.task(id:)` loop, not an inline timer publisher; UI tests pin an emote through `MASCOT_EMOTE`. The manager bow tie is deep navy, not red.

## Before timeline

- Before scroll content has explicit top clearance from the three-label navigation. On iOS 18+, `onScrollGeometryChange` and `onScrollPhaseChange` drive chrome visibility without a competing `DragGesture`: 24pt of travel toward later content hides navigation/composer, 12pt back toward earlier content reveals them, and the top 8pt always reveals. iOS 17 deliberately keeps the chrome visible because it has no equally reliable public SwiftUI offset API. `HomeTimelineView` is the single visibility source, restores it when horizontal paging begins or the page changes, ignores vertical visibility events during horizontal paging, and keeps navigation/composer identities alive with opacity/offset/hit-testing changes so composer draft state survives; Reduce Motion removes the translation.
- Timeline is the detail/index layer; Product Cards are the summary layer. A white Timeline Cluster remains a time-bound, drill-down timeline segment and is not a `CardType`. Do not flatten either layer into the other or apply Liquid Glass to timeline content.
- Explicit Input points are currently limited to `text`, `url`, `voice`, and `image`. Preserve their two-line Point presentation, native 44pt `Button`, full VoiceOver value, and lack of card surface or disclosure chevron. `save_note` and unprovenanced `idea` are deliberately not classified as Input.
- A historical Daily Briefing is a one-line date-header entry, has no rail node, and does not contribute to Event count. Its stable destination is the briefing `CardRecord.id`; the full Card Group belongs on a separate history page.
- Current `TimelineDisplayItem` salience and cluster projection are preview/MVP heuristics, not shared-contract authority. Stable item identity, provenance, cluster children, and typed destinations still require a separate contract review before changing `packages/shared` or `Models.swift`.
