## 二、吉祥物与五维属性

### 5. 职业系统（新增概念）🟡

**PRD 原文**（§4.1）：

> 定位类似 Claude Code 的 Claw：**品牌情感载体**，不是游戏角色。
> 实现：小动画、小装饰……表情图 **1~3 张封顶**——美术预算全部投在这里。**不由属性驱动、无换装体系**；v0.5 的状态立绘、结算画面、角色包规范移除（P2）。

**现状**：按昨日行为分配**职业**（Coder 等），吉祥物在早报卡中作为视觉中心呈现该职业。

**冲突程度**：比字面小 —— 设计稿中职业是**纯文字**，吉祥物未换装。但已确认后续要加"小装饰衬托职业"，**那一刻即构成属性驱动的视觉变化**，§4.1「不由属性驱动、无换装体系」需要修订。

**美术成本**：装饰保持通用（光晕/颜色/小配件）时，仍是一份主体资产 + 少量装饰，未突破 §4.1 的预算意图。若发展为整套换装则完全冲突。

### 6. 五维呈现层级 🟡

**PRD 原文**（§4.3，原文标注**「面向大众的硬约束」**）：

> briefing 卡以**状态标签 + 一句归因**打头（「昨天：疲惫。睡了 5 小时，但代码写了 4 个钟头」），**五维数值收在展开/详情层，不把数值条/雷达图直接怼给用户**；文案基调是**描述你的一天，不是给你打分**。

**现状**（设计稿）：五维五行直接展示在早报主卡片，右侧带数值列。

| 约束 | 是否满足 |
|---|---|
| 不用雷达图/数值条 | ✅ 用列表形式 |
| 每行有归因文案 | ✅ 「收入了 17 个 idea、10 张图片」 |
| 基调是描述而非打分 | ✅ 文案化 |
| 数值收在展开/详情层 | ❌ 数值在主视图 |
| 以状态标签打头 | ❌ 打头的是职业（见下条） |

**结论**：§4.3 需要修订最后两条，前三条精神保留。

### 7. 状态标签（characterState）的位置 🟡

`CharacterState` = `tired / productive / focused / inspired / normal`，与**职业**是两个不同概念，不可互相替代。

**PRD 原文**（§4.3）：状态标签是 briefing 卡的开场。

**现状**：设计稿开场被职业占据。

**已确认方案**：状态作为**卡片内的 tag** 呈现，位置参考 Apple「睡眠评分」详情页中「94 / 高」的「高」——即评级标签与主视觉并列，下方接五维明细。

---

### 8. 吉祥物动画范围扩大 🟡

**PRD 原文**（§4.1 / §4.3）：

> 小动画、小装饰（类 Claw：idle 眨眼/摆动、问候时的小点缀），SwiftUI 内建动效实现，**表情图 1~3 张封顶**
>
> 状态驱动吉祥物**动画选择**为 P1

**现状**：新增「对话时吉祥物跳到 input 框上、变小、走来走去」。

**资产前提**：Figma 中手、脚、眼睛已是独立 SVG，需**分层导出为多个 imageset**，在 SwiftUI 中各自动画。单张合并图只能整体位移/缩放/旋转，做不出迈腿和眨眼。

**成本**：超出「表情图 1~3 张封顶」的预算描述，但仍属"小动效"性质，非立绘体系。

## 五、早报卡的数据决策 🟡

三条均已拍板，**全部需要后端配合**，构成一次契约变更。前端在字段到位前用假数据占位推进。

### A. 五维数值：不算总分 ✅ 已定

沿用契约现状——五维各自独立展示，**不求和、不设总分**。

```swift
/// Five-dimensional stats, all 0–100. Computed by code on the Pi, never LLM.
struct Stats: Codable, Equatable {
    var intake, focus, output, continuity, energy: Double   // 0–100
}
```

与参照物的差异：Apple 睡眠评分是 `得分/满分` 且总分为三项之和（`94 = 50+26+18`）；ReTurn **只借鉴其行式布局，不借鉴总分机制**。设计稿中卡片顶部不出现总分数字。

### B. 归因文案：Server 出数据，前端套模板 ✅ 已定

「收入了 17 个 idea、10 张图片」「做了 6/17 个 Todo，Agent 为你工作了 10 小时」

**分工**：server 提供**分项计数**，客户端持有文案模板并本地化。

**契约影响**：`BriefingCardContent` 需新增分项计数字段。现有字段只有 `summary / openingLine / briefing / reviewPoints / stats / characterState / nodeIds`，无法拼出上述任何一句。

**待后端明确**：每个维度分别需要哪些计数项（如 intake → idea 数、图片数；output → todo 完成数/总数、agent 工作时长）。这决定模板的形参，前端需要这份清单才能定稿模板。

### C. 职业字段：Server 下发 ✅ 已定

不采用客户端推导。

**契约影响**：`BriefingCardContent` 新增职业字段；需同步 `packages/shared` Zod schema 与 `Models.swift` 镜像（AGENTS.md 要求同一 commit）。

**建议**：职业按 PRD §4.2「五维由代码确定性计算、LLM 不打分」的原则，在 server 侧也应是**确定性映射**而非 LLM 判定。枚举值建议在 shared 中固化，客户端按 `TolerantEnum` 容错（未知职业回落到默认展示），避免后端新增职业时旧版客户端崩溃。

## 六、卡片体系 🟡

### 6.0 前置：卡片与时间线是同级概念，不可混排

PRD 第 9 行：「卡片（总结层）与时间线（明细层）**概念同级**」；F7：「卡片是总结，时间线是想细看时的展开」。

| | 卡片 | 时间线 |
|---|---|---|
| 层次 | **总结层** | **明细层** |
| 内容 | 概括 | 详细 |
| 交互 | **天然可点击**——点进去看详情 | 已经是详情 |

**卡片的可点击性是其定义属性**，不是可选装饰。这也是 Apple 健康每张卡右上角都有 chevron 的原因。设计与实现中不得把明细直接铺进卡片、也不得把卡片当作时间线的条目——两者是同一信息的两个层级，靠"点进去"连接。

> 时间线中出现的白色圆角富条目（如 Agent 会话那条）**不是卡片**，它是时间线内部的一种富条目样式，只是借用了同一套视觉语汇。

### 6.1 三层模型（新概念，PRD 无对应）

PRD 只有「卡片」一个概念。实际需要三层：

```
CardType（后端数据单元）  →  卡片组（视觉分组）  →  卡片（白色圆角块）
    briefing            →   Daily Brief        →  [职业卡, Summary 卡, ReviewPoints 卡]
```

**一条后端记录可渲染成多张视觉卡片。** 设计稿中两张卡的头部都写 "Daily Brief"，即头部标的是**组名**而非单卡名。

### 6.2 需要设计的全部卡片形态（8 个）

**Daily Brief 卡片组**（来自 `briefing`，Now / Before）：

| 卡片 | 内容 | 状态 |
|---|---|---|
| 职业卡 | 吉祥物（视觉中心）+ 职业名 + 状态 tag + 五维明细行 | 设计稿已定 |
| Summary 卡 | `summary`（2–5 句叙述） | 设计稿已定，字段已定（见 6.3） |
| ReviewPoints 卡 | `win / miss / insight / other` 分类行 | ✅ 已确认独立成卡 |

**After 页**（三种独立 `CardType`）：

| 卡片 | 契约字段 | 特殊约束 |
|---|---|---|
| Todo 建议卡 | `todos[]` / `todoIds[]` | **产品定位是「提醒事项」**（见下）；唯一带副作用动作的卡 |
| 健康建议卡 | `advice` / `sleepMinutes?` / `steps?` | F12：数据必须真，文案从简 |
| 灵感卡 | `text` / `provenance` | F9 **硬约束**：必须视觉区分 `user` / `auto` 两种来源 |

**非后端卡片**（易漏，但不能省）：

| 形态 | 来源 | 说明 |
|---|---|---|
| 未 Save 提示卡 | 客户端本地，读 `/api/stats/today` 的 `saved` | 吉祥物居中 + 下方操作按钮。**不是 `CardType`**，不入卡片流 |
| 未知卡片兜底 | `CardType.unknown` / `CardContent.raw` | 见下 |

**关于兜底形态**：`CardType` 与 `CardContent` 都做了容错设计（`TolerantEnum` + `.raw([String: JSONValue])`），目的是后端新增卡片类型时旧版客户端不崩。但容错只保证"不崩"，**屏幕上显示什么仍需设计**——至少要有最小形态（组名 + 一句"这个版本还不支持显示这张卡"）。

### 6.2.1 Todo 建议卡的产品定位：提醒事项 ✅ 已定

它不是一个泛化的"待办清单"，产品上要做的是**Apple 提醒事项**。这与 PRD §6.3 的偏好回环是一致的：

> AI todo 建议卡上的「采纳」动作 → UI 端经 EventKit 写入 Apple 提醒事项；提醒事项被采样器回采（`reminder` 节点）构成**正样本**

即真实的清单永远住在提醒事项里，卡片只提**建议**。这决定了：

- 卡上的动作是「采纳」（写入提醒事项），不是「完成」（勾掉）——勾选状态的权威在提醒事项，不在这张卡
- 需要 EventKit **写权限**
- 建议须与提醒事项中未完成项查重（PRD F5 已有此要求）

### 6.3 字段落位 ⚠️ 存在语义偏差

`BriefingCardContent` 字段与实际语义（来自 `packages/server/src/ai/ferment.ts` 的发酵 prompt 与 `packages/shared/src/ferment.ts` 注释）：

| 字段 | **真实语义** | 落位 |
|---|---|---|
| `stats` + `characterState` + 职业(待加) | 五维 / 状态 / 职业 | 职业卡 |
| `reviewPoints` | 2–6 条具体的 wins/misses/insights | ReviewPoints 卡 |
| `openingLine` | **一句**温暖的话，用于次日问候 / 早报标题 | **吉祥物问候**（非卡片） |
| `summary` | **2–5 句**，讲这一天是关于什么的 | **Summary 卡** |
| `briefing` | `summary` 的**可选长版，省略时等于 summary** | **不展示** |
| `nodeIds` | 节点引用，不直接展示 | — |

**已定：Summary 卡接 `summary`，`briefing` 不展示。** ✅

判定依据是「每个字段都要有唯一归属」倒推：`openingLine` 有专属用途（PRD §9 演示脚本「Now 收到问候」），若被 Summary 卡占用则 `summary` 无处安放；反之各归其位，无冗余也无遗漏。设计稿里那句 `Put away the design work, do the art work.` 只是示例文本较短，`summary` 的 2–5 句在该卡版面内放得下。

`briefing` 默认等于 `summary`，展示会造成同一段话出现两遍，故不展示。

**待定：`streak` 契约缺口。** 🔵
PRD §4.3「streak 保留为 briefing 卡上的一行文本」，但 `BriefingCardContent` **无 streak 字段**（仅 `SaveResponse` 有，见 `packages/shared/src/api.ts:163`）。与职业、分项计数一并纳入待提的契约变更。

**命名冲突提示**：概念层的「Briefing = 卡片组（包）」与契约层的 `briefing: String`（一个文本字段）是两回事，文档与代码中需区分，建议 UI 层统一称 **Daily Brief 卡片组**。

### 6.4 页面归属：类型 + 日期的函数 ✅ 已确认

归属**按概念**判定，而非按类型静态绑定：

| 页面 | 概念 |
|---|---|
| **Now** | 用户现在就要知道的（今天的早报） |
| **After** | 之后要做的、之后建议的（todo 建议、健康建议、灵感） |
| **Before** | 已经过去的 |

推论（PRD 第 42 行已隐含：「次日打开 Now 收到问候 + briefing；**Before 流顶部出现昨日卡片**」）：

| 卡片类型 | 归属规则 |
|---|---|
| `briefing` | `date == 今天` → **Now**；否则 → **Before** |
| `todo_suggestion` / `health` / `idea` | 恒为 **After** |

**因此 Before 会积累全部历史早报，是内容最重的一页**，而非最少。

Before 同时承载卡片（总结层）与时间线（明细层），但按 6.0 两者不可混排——历史早报卡是总结，点进去才是当日时间线。

### 6.5 统一卡片外壳

三级规格，收进 `DesignTokens`：

- **组级**：组名 + 组图标（如 `📖 Daily Brief`）、组内卡片间距、组间距、可选分组大标题（设计稿中的 "Summary" 即是）
- **卡级**：白底 / 圆角 / 内边距 / 卡内分隔线 / 头部（图标 + 标题 + 右侧次要信息 + **chevron，对应 6.0 的可点击性**）
- **行级**：彩色圆点或图标 + 名称 + 右侧数值 + 下方灰色归因文案。五维、reviewPoints、健康建议共用此规格

**强调色只出现在标识位**（图标与分类名），正文保持黑/灰——这是 Apple 健康「活泼但不花」的关键。

### 6.6 卡片之间要有区别 🟡

外壳统一 ≠ 每张卡长得一样。参照 Apple 健康——各卡片**既非雷同、也非各行其是**，差异控制在一个受限的范围内：

| 层面 | 处理 |
|---|---|
| **共用**（保证整齐） | 白底、圆角、内边距、头部结构、chevron、行式布局、字体层级 |
| **差异**（保证识别度） | 主视觉元素、数据呈现方式 |

Apple 健康的实例：环境音量卡用条形图 + 蓝色基准横线；步数卡用折线图 + 今天/平均双列对比；睡眠评分卡用分段环形图 + 评级标签。三张卡一眼能区分，但明显是同一套系统。

**ReTurn 对应**：职业卡的主视觉是吉祥物 + 职业名 + 五维行，Summary 卡是纯文本，ReviewPoints 卡是分类行——已天然具备差异，需确保差异落在"主视觉元素"这一层，而非各自发明外壳。

> 具体每种卡片的设计由产品方另行详述，本节仅记录原则。

### 6.6.1 颜色规则：可以分类，不可以评判 ✅ 已定

这条是实现过程中试错定下来的，比"外壳统一、差异在主视觉"更具体，也更容易被无意违反。

**基线**：一张卡一个强调色，只出现在**头部图标与标题**上。卡内其余一切用 primary / secondary label。Apple 健康的耳机音量卡通篇只有蓝、步数卡只有橙。

**允许的例外**：颜色用来**分类**时可以出现在卡内——五维明细行的色点即属此类，性质等同 Apple 睡眠评分给三个分项上色，是图例，不含褒贬。

**禁止的用法**：颜色用来**评判**。ReviewPoints 曾用绿色标「做到了」、橙色标「没做到」，这会把卡片变成一张成绩单，直接违反 PRD §4.3：

> 文案基调是**描述你的一天，不是给你打分**

现改为符号无色、仅靠形状区分（`checkmark.circle` / `circle.dashed` / `lightbulb`），且用描边而非填充变体——填充符号对次要标记来说过重。

**判据**：给某处上色前问一句，这个颜色是在说"这属于哪一类"，还是在说"这是好事还是坏事"。后者不加。

### 6.6.2 Health 的三条实现纪律

同样是试错得来的，第一版全都违反过：

1. **分隔线标记"内容换层"，不是"头部结束"。** 节奏是 头部 → 一句话结论 → 分隔线 → 数据；结论后无内容的卡（如 Summary 卡）**一根线都不画**。
2. **明细行统一 regular 字重、body 字号**，靠 primary / secondary 的黑灰对比分主次。全用 semibold 会把层级压平成噪音。
3. **留白要足**：卡片内边距 20、圆角 22、组间距 32，每行上下各 9pt，使分隔线落在真正的空白中而非贴着文字。行内留白需按行数调整——五维有五行，沿用睡眠评分（三行）的间距会把卡片撑得过长。

### 6.7 与 Before 时间线的对齐

Before 时间线由**另一位 agent 负责**，本文件不涉及其实现，仅记录需要共用的约定。

时间线**借用了与卡片相同的视觉语汇**（彩色图标 + 同色分类名 + 黑色主标题 + 灰色次要信息），但按 6.0 它属于明细层，不是卡片。两点应统一到 Now 侧：

1. **轻重分级**：轻量条目仅一行，重条目才升级为白色富条目并内嵌浅灰子列表。卡片侧同理（如 streak 一行文本不必成卡）。
2. **标题层级**：时间线有 `FRIDAY` / `Jul 24` / `12 Events` 三级；Now 页目前无标题层级，两页需一致。

**色板：等待产品方统一分配后另行通知，本轮不设计。** 🔵
仅记录冲突风险：时间线已占用 Sleep 紫 / Voice 青 / Design 品红 / Agent 橙 / Git 灰 / Text 绿；早报五维与各卡片组也需配色，两套须收进同一 token 命名空间，否则同一颜色在不同页面表示不同概念。

当前实现的占位色集中在 `ReTurnDesign.Colors.Accents`，视图层无任何硬编码颜色，替换为正式色板是**改一个 enum** 的工作量。

### 6.8 尚未归位的三件事 🔵

均在讨论中浮现但未拍板，会阻塞相应实现：

**1. 「待确认项」的形态。**
PRD §3 F3 写 Now 承载「Task 回传与**待确认项**」，但契约中没有对应的 `CardType`。它是卡片、是消息、还是第三种形态？

**2. Task 回传的通道。**
判断是走 `messages` 而非 `cards`——PRD §5 的表结构里 `messages` 带 `task_id` 字段（`-- Now 区对话流`）。**需确认**，若成立则 Task 回传不需要卡片设计。

**3. 卡片详情页。**
§6.0 已定「卡片可点击进入详情」是卡片的定义属性，那么**每张卡点进去是什么**也需要设计。至少要区分：哪几张有详情（如职业卡 → 当日时间线、Review 卡 → 相关节点），哪几张点进去无意义（如 Summary 卡可能没有更细的内容可展开——当前实现已对它省略 chevron）。
