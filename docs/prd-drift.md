## 一、主视图导航

### 1. 滑动方向：上下 → 左右 🟢

**PRD 原文**（§0 变更摘要 / §3 F3）：

> 主视图变为以 **Now** 为锚点的**双向时间流**：上刷 Before（回溯过去），下刷 Future（建议与灵感）
>
> F3：以 Now 为锚点的一条**上下滑动**流

**现状**：三页**左右**滑动 pager（`TimelinePage.before/now/after`），顶部标签与滑动位置共享同一 selection，默认停在 Now。

**影响**：PRD §3 F3 描述需重写；"上刷/下刷"在全文多处出现，合并时需全局检查。

---

### 2. 命名：Future → After 🟢

**PRD 原文**：全文使用 `Future`。

**现状**：代码使用 `After`（`TimelinePage.after`），UI 标签显示 "After"。

**影响**：纯命名，但契约、文档、UI 三处需统一。合并 PRD 时决定以哪个为准。

---

### 3. sidebar：左滑 → 上滑 🟡

**PRD 原文**（§3 F3）：

> **左滑** sidebar：空间身份 / 进行中 task / 设置&关于

**现状**：改为"向上滑动露出"，**本轮未实现**，Before/After 目前是空白占位页。

---

### 4. 顶部导航样式（PRD 无约束，记录以备参考）🟢

segmented `Picker` → 三个纯文字 label；静止 1.5s 后淡到 0.3（不隐藏，保持可点）；滚动时立即恢复全强度。

理由：实心灰胶囊是全屏唯一不透明的面，与扁平吉祥物、半透明 composer 不是一套视觉语言。

## 二、吉祥物与五维属性

### 5. 职业系统（新增概念）🟡

**PRD 原文**（§4.1）：

> 定位类似 Claude Code 的 Claw：**品牌情感载体**，不是游戏角色。
> 实现：小动画、小装饰……表情图 **1~3 张封顶**——美术预算全部投在这里。**不由属性驱动、无换装体系**；v0.5 的状态立绘、结算画面、角色包规范移除（P2）。

**现状**：按昨日行为分配**职业**（Coder 等），吉祥物在早报卡中作为视觉中心呈现该职业。

**冲突程度**：比字面小 —— 设计稿中职业是**纯文字**，吉祥物未换装。但已确认后续要加"小装饰衬托职业"，**那一刻即构成属性驱动的视觉变化**，§4.1「不由属性驱动、无换装体系」需要修订。

**美术成本**：装饰保持通用（光晕/颜色/小配件）时，仍是一份主体资产 + 少量装饰，未突破 §4.1 的预算意图。若发展为整套换装则完全冲突。

---

### 6. 五维呈现层级 🟡

**PRD 原文**（§4.3，原文标注**「面向大众的硬约束」**）：

> briefing 卡以**状态标签 + 一句归因**打头（「昨天：疲惫。睡了 5 小时，但代码写了 4 个钟头」），**五维数值收在展开/详情层，不把数值条/雷达图直接怼给用户**；文案基调是**描述你的一天，不是给你打分**。

**现状**（设计稿）：五维五行直接展示在早报主卡片，右侧带数值列。

| 约束 | 是否满足 |
|---|---|
| 不用雷达图/数值条 | ✅ 用列表形式 |
| 每行有归因文案 | ✅ 「收入了 17 个 idea、10 张图片」 |
| 基调是描述而非打分 | ✅ 文案化 |
| 数值收在展开/详情层 | ❌ 数值在主视图 |
| 以状态标签打头 | ❌ 打头的是职业（见下条） |

**结论**：§4.3 需要修订最后两条，前三条精神保留。

---

### 7. 状态标签（characterState）的位置 🟡

`CharacterState` = `tired / productive / focused / inspired / normal`，与**职业**是两个不同概念，不可互相替代。

**PRD 原文**（§4.3）：状态标签是 briefing 卡的开场。

**现状**：设计稿开场被职业占据。

**已确认方案**：状态作为**卡片内的 tag** 呈现，位置参考 Apple「睡眠评分」详情页中「94 / 高」的「高」——即评级标签与主视觉并列，下方接五维明细。

---

### 8. 吉祥物动画范围扩大 🟡

**PRD 原文**（§4.1 / §4.3）：

> 小动画、小装饰（类 Claw：idle 眨眼/摆动、问候时的小点缀），SwiftUI 内建动效实现，**表情图 1~3 张封顶**
>
> 状态驱动吉祥物**动画选择**为 P1

**现状**：新增「对话时吉祥物跳到 input 框上、变小、走来走去」。

**资产前提**：Figma 中手、脚、眼睛已是独立 SVG，需**分层导出为多个 imageset**，在 SwiftUI 中各自动画。单张合并图只能整体位移/缩放/旋转，做不出迈腿和眨眼。

**成本**：超出「表情图 1~3 张封顶」的预算描述，但仍属"小动效"性质，非立绘体系。

## 三、Now 区

### 9. Now 状态机（细化，非冲突）🟡

**PRD 原文**（§3 F3）：

> Now 承载对话消息、问候、吉祥物、Task 回传与待确认项（平时折叠/半隐藏，有内容时展开）

**现状**：明确为四态，且**空状态不作为常态展示**：

| 状态 | 视觉中心 | 吉祥物位置 |
|---|---|---|
| 早上·有未读早报 | Daily Brief 卡 | 卡内，作为职业视觉中心 |
| 白天·今天未 Save | 提示卡 + 操作按钮 | 中心，按钮在其下方 |
| 对话中 | 对话消息流 | 跳到 input 框上走动 |
| 真空状态（首日等） | 吉祥物问候 | 中心 |

**状态判定数据源**：`GET /api/stats/today` 已返回 `saved: Bool` 与 `cadence: .active/.night`，**无需在客户端硬编码时间阈值**。

## 五、早报卡的数据决策 🟡

三条均已拍板，**全部需要后端配合**，构成一次契约变更。前端在字段到位前用假数据占位推进。

### A. 五维数值：不算总分 ✅ 已定

沿用契约现状——五维各自独立展示，**不求和、不设总分**。

```swift
/// Five-dimensional stats, all 0–100. Computed by code on the Pi, never LLM.
struct Stats: Codable, Equatable {
    var intake, focus, output, continuity, energy: Double   // 0–100
}
```

与参照物的差异：Apple 睡眠评分是 `得分/满分` 且总分为三项之和（`94 = 50+26+18`）；ReTurn **只借鉴其行式布局，不借鉴总分机制**。设计稿中卡片顶部不出现总分数字。

### B. 归因文案：Server 出数据，前端套模板 ✅ 已定

「收入了 17 个 idea、10 张图片」「做了 6/17 个 Todo，Agent 为你工作了 10 小时」

**分工**：server 提供**分项计数**，客户端持有文案模板并本地化。

**契约影响**：`BriefingCardContent` 需新增分项计数字段。现有字段只有 `summary / openingLine / briefing / reviewPoints / stats / characterState / nodeIds`，无法拼出上述任何一句。

**待后端明确**：每个维度分别需要哪些计数项（如 intake → idea 数、图片数；output → todo 完成数/总数、agent 工作时长）。这决定模板的形参，前端需要这份清单才能定稿模板。

### C. 职业字段：Server 下发 ✅ 已定

不采用客户端推导。

**契约影响**：`BriefingCardContent` 新增职业字段；需同步 `packages/shared` Zod schema 与 `Models.swift` 镜像（AGENTS.md 要求同一 commit）。

**建议**：职业按 PRD §4.2「五维由代码确定性计算、LLM 不打分」的原则，在 server 侧也应是**确定性映射**而非 LLM 判定。枚举值建议在 shared 中固化，客户端按 `TolerantEnum` 容错（未知职业回落到默认展示），避免后端新增职业时旧版客户端崩溃。
